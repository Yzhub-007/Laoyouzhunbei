# 涝有准备：浙江大学紫金港校区试点落地方案

版本：v0.4；编制日期：2026-10-02。校区由团队确认；具体楼宇、管理联系人、学校授权、正式预案和模型API尚待提供。本文是执行方案，不是校方文件或已完成试点报告。

## 1. 首期到底交付什么

交付一个用于楼宇管理的防汛信息与行动工作台：管理人员输入有来源的天气资料、核实过的点位台账与现行工作条目，系统整理待审核任务，人工核验后记录处理状态、整理公众提示草稿和反馈。首期只覆盖紫金港一个获得同意的楼宇及周边通道，5—8个点位。

成功的最低定义：一位负责该范围的管理人员能够用自己的资料完成“查来源→看任务→改错→确认→整理提示→回看记录”，并愿意约定下一次试用。研究问题是是否改善资料查找、任务整理和信息理解，不是预测积水、水深或最安全路线。

已有公开背景：[浙大国际教育学院官网](https://iczu.zju.edu.cn/lxwm_62704/list.htm)列有紫金港校区余杭塘路866号地址；[艺博馆历史通知列表](https://zjumaa.zju.edu.cn/p74282c71798/list5.htm)保留了2021年7月24日防台背景下的临时闭馆公告。这些资料支持校区背景和历史通知回放，不证明当前存在积水、某入口关闭或管理方已同意试点。[后勤集团官网](https://zulg.zju.edu.cn/index.htm)作为公开信息入口，不替代内部职责表和正式预案。

## 2. 范围与参与者

| 要素 | 首期安排 | 进入下一阶段的凭据 |
|---|---|---|
| 区域 | 一个楼宇＋周边通道；边界由管理方确认 | 楼宇名称、边界描述、示意图或台账引用 |
| 管理人员 | 2—3名实际有相关职责的人员 | 自愿参与记录、职责范围、资料使用许可 |
| 学生/公众 | 8—12名，编号S01起 | 自愿参加说明与匿名记录 |
| 团队 | A负责软件/API/日志，B负责场地/资料/试验主持 | 每日交接表 |
| 点位 | 5—8项，按实际存在的设施建档 | 来源、核验人角色、核验时间 |
| 预案 | 5—10条获准工作清单或正式条款摘录 | 条款编号、适用范围、角色、版本、审核人 |
| 运行 | 先桌面演练，再5个工作日影子观察 | 准入检查和负责人同意 |

目前未获知团队可接触的管理人员类型，因此联系路径保持两条：有管理联系人时直接选择其负责的一栋楼；只有学生团队时，通过指导教师或学院协调一位管理联系人，先做学生可用性探索。后者不能写成机构试点或管理人员验证。

不预先命名“浙大易涝点”。程序中的地下入口A、入口B、通道C/D、室外设施E、信息联络点F只是采集槽位；没有对应真实设施时删除或替换，不为凑数量编造点位。图书馆、宿舍或学院楼只是可选场景，不代表已达成合作。

本版是可运行的桌面演练与影子观察原型。影子运行的输出仍只供旁路核对，管理决定走学校现有流程；没有自动向师生发消息、控制设施、发出巡查调度或自行发布预警的接口。

## 4. Agent的实际工作方式

采用一个受约束的编排Agent，内部调用确定性工具及一个可替换模型适配器，不让多个自由对话Agent互相投票。

1. **接收与版本化**：读取本次天气、点位和预案快照，生成SHA-256指纹；不自动从互联网抓取任意用户链接。
2. **检查资料**：校验必填、时间先后、来源URL、编号、地区、校区及运行阶段。桌面演练允许待核实资料，影子运行须具备授权/边界/点位/条目/校区五项记录，并使用新近快照。
3. **限定范围检索**：仅保留同城市、同校区、匹配灾种与点位类型、指定点位范围和有效期内的条目。城市天气参考不能直接证明点位受影响。
4. **条目选择**：规则基线选择全部候选；AI模式把白名单资料与候选集合交给配置模型，只允许返回已有点位/条目编号。
5. **核验与交接**：拒绝多余字段、无效引用和不适用组合；使用预案原文组装任务及角色；保留AI未选择候选供人工检查。
6. **人机闭环**：负责人修改/确认后跟踪执行；公众提示依据单独的人工现场状态生成。完成任务不自动等于入口开放或现场安全。

模型输出的优势尚未证实。当前范围规则已能处理大部分结构化匹配，AI可能不比模板更好。只有试验显示其帮助管理人员减少查找或修改时间、且不增加错误，才保留更大职责；否则以规则为主，缩小AI用途。未来可单独研究长预案条款提取，但本版不宣称已实现PDF自动解读或自然语言风险推断。

## 5. 资料建档与替换

第一轮建档在天气适宜、管理方同意的正常工作条件下完成，可由管理人员提供既有照片/台账代替现场拍摄。学生不为测试进入地下、设备间或恶劣天气现场。

每个点位至少填写：编号、实际名称、位置与边界描述、真实类型、已确认特征、来源记录、核验角色与时间。未知特征写“未知”。同名入口使用不同编号。

每个条目至少填写：编号、标题、灾种、点位类型、任务原文、责任角色、来源条款、审核角色与时间；需要时填写`point_ids`、`campus`、`valid_until`。原件只保留获准使用的片段，不复制整个内部文件。

网页“试点资料建档”可逐项编辑；高级字段和5—8个点位的增删可在“点位与条目→完整JSON”中完成，再回到建档保存。JSON采集模板位于`data/zju_pilot.json`。程序只验证凭据完整性，不能验证授权人身份或文件真实性。

## 6. API接入边界与验收

后续需要：服务商名称、完整接口地址、协议文档、模型名称、可用限额，以及是否允许发送获准资料。密钥只填写本机`.env`，不要发到聊天。当前适配`messages`请求和`choices[0].message.content`响应；不支持的协议需按文档另写适配器，不能仅替换URL。

先用完全合成资料验证一次成功和超时/鉴权失败，再检查真实资料发送范围，最后开展正式测试。网页可本机预览待发送字段，不触发付费调用。授权凭据、核验人、试验参与者和评分字段不会自动发送；原文里残留的个人信息仍需人工脱敏。

不配置API时，规则演练、建档和计时工具都可用；AI按钮保持不可用，正式AI结果留空。没有假模型结果填补缺失。

## 7. 四周执行节奏（20个工作日）

此为规划，不假设团队已经启动；若比赛只剩两周，完成桌面阶段并如实标注影子观察待开展。

| 工作日 | A：技术负责人 | B：场景与验证负责人 | 必须产出 |
|---|---|---|---|
| D1—2 | 安装演示、检查本机数据 | 联系管理人员，选楼宇，确认资料许可 | 一页范围和联系人角色表；无联系人则转探索路线 |
| D3—4 | 录入和检查字段 | 与管理方核实5—8点位、5—10条任务 | 台账v1、工作条目v1、来源凭据 |
| D5 | 联调Agent与API（若已提供） | 管理方逐条审核任务与提示措辞 | API回执或“未配置”；修订清单 |
| D6—7 | 开发案例调试、修复 | 主持一次练习轮 | 缺陷记录、可操作演示 |
| D8 | 冻结代码、模型、参数、输入版本 | 独立制作留出案例、评分表与分配表 | 冻结清单，开始后不得调参 |
| D9—10 | 跑规则/AI技术留出测试 | 管理人员参考答案复核 | 包含失败的技术报告；关键错误未解则止步 |
| D11—12 | 支持计时与导出 | 2—3名管理人员三条件任务 | 匿名任务记录及观察意见 |
| D13—14 | 支持通知素材整理 | 8—12名公众理解测试 | 问卷、顺序分配、匿名得分 |
| D15—19 | 仅维护阻断问题、留存故障 | 满足准入后开展5工作日影子观察 | 日志与现行流程差异；没有天气事件也如实记录 |
| D20 | 汇总指标、运行成本、失败回归 | 回访负责人、确认是否再试 | 结论、继续/收缩/停止决定 |

出现严重事实错误，暂停真实影子阶段，保留旧失败数据；修复后新版本另建记录并复测，不能替换旧结果。真实气象事件期间，测试安排服从现有工作，不追加学生巡查。

## 8. 资源与成本记录

采用已有电脑、现有浏览器和Python标准库，无需购买传感器。首期单机由主持人操作；若多人需要在手机实时协同，必须进入认证、校内HTTPS和权限管理建设阶段，不能把本机服务直接开放公网。

预算建议作为团队内部上限：API试验预留300元、资料打印与校内协调预留100元，总预留400元；这不是服务报价，也不是实际支出。启用前按服务商实际价格重新计算。人工时间单独记录，不因学生投入而记为“零成本”。

模型费用按成功和失败调用的实际账单统计；有usage时记录输入/输出token，缺失则写未提供，不估造。每个成功任务成本=该条件全部调用实际费用/完成任务数，另报告失败调用数和人工维护分钟数。

## 9. 成功标准和下一步决策

试点准入标准是设计目标，不是已达结果：关键事实错误为0；所有任务可定位资料来源；公众不将未知误认作安全；记录可恢复；没有因API失败丢失人工流程。

性能是否有益按相同难度场景报告中位耗时、每人变化、错误/遗漏/无依据建议的原始计数。小样本不用“提高X%”作为事先承诺，也不把小样本描述性变化当作普遍结论。

继续条件：负责人愿意再次试用、资料维护责任人明确、错误可控、额外维护负担可接受。收缩条件：规则足够，AI不改善使用体验；保留规则与审核。停止条件：无管理联系人、关键错误反复出现、数据授权不明确或无人维护台账。

下一阶段可考虑同校区第二栋楼的资料迁移试验，再讨论多用户与官方预警接入；不同时扩展到全校地图、预测模型和自动发布。

完整主持脚本、评分、分组和数据封存见[完整试验流程](11_紫金港完整试验流程.md)。接口配置和开发调用见[Agent与API约定](12_Agent与API接入约定.md)。
